# 上下文管理：已有方案与下一阶段

本文基于当前源码核对能力。**可恢复原始记录、能够压缩历史，并不等于已经解决语义漂移。** 以下设计建议尚未实现，不作为产品保证。

## 三种不同的问题

| 问题       | 例子                                             | 应对方向                                         |
| ---------- | ------------------------------------------------ | ------------------------------------------------ |
| 记录不一致 | 某位成员看到了新约束，其他成员没有               | 固定公开快照、稳定身份、请求投影审计             |
| 语义漂移   | 摘要把“暂时倾向”改成“已经决定”，早期禁止事项消失 | 固定任务约束、结构化状态、摘要验证与回取原文     |
| 窗口耗尽   | 输入本身过大，或加上输出/推理预算后超限          | 各模型预算、分层压缩、按需检索、有边界的失败恢复 |

更多 token 不能自动解决语义漂移；只有来源 ID 也不能证明摘要忠实。

目前可使用：

    /memo add 用户禁止删除原始记录
    /memo agent 2 保留你尚未解决的不同意见
    /context
    /context full
    /context budget 24000
    /context auto on
    /compact 1
    /history

上述命令能控制输入与检查记录，不构成模型理解一致或结论正确的证明。

## 当前缺口

### 来源合法不等于语义正确

压缩回答的 sourceIds 必须来自被压缩的消息，但未检查每项关键约束、决定、不同意见是否被忠实保留。sourceIds 记录覆盖范围，citedSourceIds 记录模型所引消息；两者都不是事实验证。摘要是一个模型生成的文本，不是其他成员逐一确认的结论。

早期用户要求可能只剩摘要里的转述。手动 memo 可以缓解，但没有自动维护的任务约束层。反复“摘要旧摘要”会累积遗漏与语义偏移，也没有定期回读原文重建的策略。

### 平台预算不是模型的真实窗口

当前字节估算不是 tokenizer，也不是可靠的 token 上界。统一预算没有读取各模型窗口，未统一扣除输出、推理和工具开销。直接 API 虽保存 usage，但未据此校准估算。调高 /context budget 不会扩大供应方的真实窗口。

压缩只在超出预算后触发；默认由第一位成员生成摘要，没有独立摘要模型或自动切换策略。摘要请求自身使用大小上限，但也没有按其供应方窗口做精确预算。

### 当前轮次可能无限增长到装不下

压缩边界是最近一次用户消息。当前用户问题之后的所有观点和判断完整保留；讨论轮数有上限，但单轮多人长回复仍可能耗尽窗口。此时继续压缩更早的历史未必有效，当前处理是暂停，而非截掉正在发生的分歧。

旧结果还会作为 priorResults 注入；记录、候选和公开判断有重复内容，尚未统一去重和按用途挑选。没有对供应方 context-overflow 错误做分类后的压缩恢复，也没有摘要内容的原文回取工具。

### 同步版本还不够完整

平台知道记录版本与成员身份，但没有持久化每次实际输入的 manifest/hash，无法准确审计“该回答实际看到了哪些字段和材料”。API、native、A2A 的执行过程不同；native 的单轮工具结果和内部压缩仍由原生运行时管理。

历史投影保留显示名称，未完整保留 authorId/role/kind/判断元数据；压缩边界还依赖显示名称“用户”。稳定角色字段应进入投影，避免成员重名影响身份和边界判断。原生成员能看到的项目工具材料，也不一定被 API 成员看见，必须区分公开记录相同与全部证据相同。

## 建议实现顺序

### P0：任务约束与预算

1.  **固定任务约束层。** 保存当前目标、用户明确禁止项、验收条件与变更来源。模型可以提出更新，平台在用户确认或明确版本规则下应用；其他成员的摘要不能悄悄改写用户约束。先支持明确配置，无需马上添加自动提取。
2.  **每位成员独立计算容量。** ContextManager 的 interface 接收模型能力与当前讨论状态，输出本次投影和 manifest。预算遵守：

        可用输入 = 模型窗口 − 输出预留 − 推理/工具预留 − 安全余量

    具体扣减遵守供应方的计数口径；推理若已计入输出预算，不重复扣除。未知窗口明确标记 unknown；平台预算继续作为用户上限。自动压缩后重新检查，失败则暂停。不能把一次数值估算包装成精确计数。

3.  **稳定角色与类型。** 原始消息的 authorId、role、kind 与判断状态进入投影；源消息关联不依赖显示名称。共享正文可一致，成员私有 memo 与预算差异要在 manifest 中显式记录。

### P1：压缩保真与当前轮次瘦身

4. **结构化 checkpoint。** 将目标、约束引用、事实/假设、决定、未决分歧、下一步分开；标记模型推断和不确定性。字段校验之外，检查必保留约束的引用覆盖。语义评审可以辅助，但不能把“另一模型认可摘要”当作正确性证明。
5. **保存当前讨论的结构化状态。** 当前候选、各成员最新 stance、未解决冲突必须完整保留；已被替代的冗长互评可以压缩，最新理由与相关反对依据保留原文。候选 ID、投票和终局判断始终读取结构化记录，不从摘要重新推断。
6. **按需回取原始证据。** 先提供按 messageId 读取或关键词搜索的工具，回取材料标注来源和版本，再考虑向量检索。检索必须防止把旧约束当成现行要求；回取原文能核对摘要，但不会自动消除理解偏差。
7. **请求投影审计。** 保存共享版本、约束版本、checkpoint ID、源消息 ID、材料版本、估算方式与预算、模型配置。需要保存完整请求时明确存储成本与敏感材料边界；hash 本身不能重建已经丢失的输入。

### P2：可衡量的防漂移

8. **建立长对话评测。** 早期埋入约束、连续多次压缩、后续修改约束、模型切换、成员加入/退出、候选修订、当前轮次爆长、错误摘要与模型真实超限。
9. **测具体结果。** 约束保留率、旧状态误用率、分歧丢失率、按来源回取成功率、压缩前后 token/cost 与无效终局率。固定数据与预期答案用于检查，不仅让另一个模型打分。
10. **有限恢复。** 将上下文超限、输出耗尽、网络失败分别处理。每种恢复限定次数与条件，记录每次尝试，不进行无限压缩重试。

## 行业方案能借鉴什么

| 方案                                                                                                                     | 可借鉴点                                                                        | 与本平台的关系                                                           |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| [Pi compaction](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md)                 | 按窗口扣除 reserveTokens；追加 checkpoint；重建摘要加近期记录；有边界的超限恢复 | 当前 checkpoint 思路已采用；模型预算和恢复策略未完整采用                 |
| [Anthropic context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)                       | 清理旧工具结果并留下移除标记，配合 memory 按需取回材料                          | 是供应方方案；本平台尚未接入这些策略，不能将供应方内部编辑视为共同事实源 |
| [DeepSeek Harness compaction](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/README.md) | 独立 compaction package 和 runtime 分工                                         | 参考 module 的职责；未集成整套框架                                       |
| [A2A contextId](https://a2a-protocol.org/latest/specification/#341-context-identifier-semantics)                         | 关联同一会话的消息和任务，允许服务自行维护历史                                  | 关联标识不规定摘要质量、统一窗口预算或跨成员语义一致性；这些仍需平台设计 |

建议把能力集中在 ContextManager 这个 module 的 interface 上，避免每个 adapter 再实现一套记忆策略。终端和网页只配置与展示，Adapter 负责传输和执行，讨论引擎负责推进候选和判断。协议互通、上下文管理和结论验证是三项不同职责。
