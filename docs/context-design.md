# Agent 运行核心与上下文可靠性

TalkWithPeer 的核心是平台拥有的记录、上下文投影、证据回取、运行预算与候选判断。终端和网页是这个运行核心的调用方。v0.3 实现了下面的优化；模型摘要的完整语义正确性仍不作为保证。

## 针对哪些问题做了什么

| 问题                           | 已实现优化                                                                                                            | 验证                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 压缩后用户约束只剩模型转述     | 用户配置的目标与固定约束独立保存；被压缩的用户指令原文再次注入，不由摘要替代。用户可显式重设指令生效边界              | 重复压缩、约束更新、用户原文保留检查                 |
| 成员重名导致身份或压缩边界混淆 | 投影保留 authorId、role、kind、记录版本和结构化判断。名为“用户”的 Agent 仍是 agent                                    | 同名成员检查                                         |
| 当前轮次越聊越大               | 允许压缩当前轮次的旧互评；保留最新用户问题、每位当前成员最新公开回复、当前候选和结构化判断                            | 当前轮次压缩后，最新反对理由与 nonNegotiable 仍存在  |
| 摘要编造引用或把观点升级为决定 | 结构化 facts/decisions/unresolved 分区，引用必须精确匹配原始公开正文；decisions 只能引用平台发布的共识结果            | 伪造 quote、引用未确认观点作为决定会被拒绝           |
| 摘要模型自身也装不下旧历史     | 按容量把文本分段，最多 64 批；每批计量后才执行，任意一批失败不替换已有 checkpoint。原生摘要请求也逐批建立新运行时会话 | 超大历史分段、失败不保存检查                         |
| 平台预算与模型窗口脱节         | 分别计算模型窗口、实际 API 输出上限、额外预留和安全余量；未知窗口明确显示 unknown，可由用户配置                       | 容量计算、非法配置拒绝、API 实际输出下限检查         |
| 简单字节估算不准               | Responses/Anthropic 使用供应方计数接口；未提供接口时使用实际 usage 校准启发式估算，始终标明来源                       | 协议计数检查与估算校准检查                           |
| 摘要说法需要回查               | Agent 可通过 readMessageIds 请求本会话公共原文，每次 1–3 条、最多两次；用户可用 /recall                               | 回取后最终回答、跨会话拒绝、无限回取暂停检查         |
| 不知道回答实际看到了什么       | 每次生成调用独立保存实际平台文本、模型参数、版本、来源、memo ID、容量、计数方式、哈希和 usage；摘要调用也审计         | 哈希核对、原文回取请求链、重启恢复与 HTTP 作用域检查 |
| 实际模型报告超限               | 协调全阶段压缩并重发一次；旧阶段已完成的回复标为 superseded，不参与新判断                                             | 一次恢复、重复超限暂停检查                           |
| 输出耗尽被误当成格式错误       | 单独标记 output_limit，暂停并保留记录，不在同样预算下反复修复 JSON                                                    | 输出不足只调用一次检查；真实 DeepSeek 已观察到该保护 |
| 仅凭“到了第二轮”误判僵局       | 要求同一候选下，双方前后两轮都保留双向 nonNegotiable 分歧                                                             | 首次出现、单向分歧与候选版本变化不能触发终局         |
| 一直由第一位成员主导初始候选   | 初始候选来源随用户轮次轮换；仍由所有成员明确判断                                                                      | 讨论收敛检查；不使用多数票                           |
| 进度每个 token 都写库并刷新 UI | 供应方公开摘要合并成一次完整事件，实时仅发布真实进度标记                                                              | 运行过程保持公开，私有内部思维仍不复制               |

## 输入投影

本轮请求有独立 latestRequestId。原始目标默认属于背景，候选和接受判断都必须回答本轮请求并遵守其篇幅和格式。解释或比较问题的适当答复可以形成共识，不要求每一轮解决整套历史目标；终局和请求审计记录关联 requestSourceId 与任务版本。

文件材料记录项目、相对路径、内容哈希和捕获时间，切换项目后不自动注入旧项目快照。平台会话身份在成员加入时建立，重启会迁移旧原生会话标识，项目切换不会清空平台身份。API 的平台规则走协议各自的 system/instructions 层，计数接口也包含该规则；记录材料仍属于用户输入层。

    原始公共消息（完整保留在 SQLite）
       + 稳定身份与角色
       + 用户拥有的任务目标 / 固定约束
       + 被压缩的用户原始指令
       + 最新 checkpoint（标记为模型转述）
       + 近期消息与当前结构化讨论状态
       + 共享 memo / 当前成员 memo
       + 显式回取的公共证据
       → 平台构建的本次输入

同一阶段使用冻结的公开快照。私有 memo 和按需回取的证据可能不同，审计记录中明确这些差异；sharedHash 用于比较相同的公共投影。原生工具自己读取的材料不自动成为其他成员的共同证据。

默认任务目标来自第一条用户消息；用户可明确配置目标与固定约束。目标和原文保存不表示旧要求永远优先：后续明确变更仍需按来源与时间理解，用户可以 rebase 旧指令边界。模型无权直接改写任务配置。

## 容量规则

    可用输入 = min(
        平台输入预算,
        已知模型窗口 − 输出预留 − 额外推理/工具预留 − 安全余量
    )

- 窗口未知时使用平台输入预算，但不声称它等于真实窗口。已知供应方窗口不会被更大的用户配置绕过；用户可设置更小的窗口作为限制。
- API 输出预留不能低于实际配置的最大输出。推理已包含在该输出上限时，不再额外重复扣除。
- 原生单轮工具和内部提示仍由原生运行时管理；额外预留由用户设置，不能精确计量隐藏的运行时输入。
- Responses 调用 /responses/input_tokens，Anthropic 调用 /messages/count_tokens；兼容服务不支持端点时回退到校准估算。认证失败不会被伪装成成功计数。
- 未观察到 usage 时标记为启发式估算，观察到 usage 后标记为校准估算，两者均不是 token 上界。供应方仍可能拒绝输入，届时只允许一次上下文恢复。
- 压缩后重新检查每位成员的完整输入。目标、用户原文、memo 或最新回复本身过大时明确暂停，不静默删掉它们。
- 摘要自身按选择的成员容量执行，并校验新 checkpoint 是否减少整个输入投影，包含重新注入的原始指令。

窗口信息取自服务明确返回的 context_window 或用户配置，不根据模型名称猜测上下文大小。

## 压缩的信任边界

Checkpoint v2 记录覆盖的原消息 ID，历史仍完整存在。模型产出的 summary、facts 和 unresolved 都是有来源的转述，不是事实证明。引文必须是原始正文中的连续文本，本批材料必须有引用覆盖；确认决定的来源还要有平台发布的 consensus 记录。

这些机械校验能拒绝虚构引用、跨会话材料及部分不合法状态升级，不能证明每一句转述都语义忠实。关键用户约束通过独立原文层保留，当前投票与候选通过结构化状态保留，不从摘要推断终局。

v0.2 的 checkpoint 作为 schemaVersion=1 读取，保留原记录和边界，不伪造 v2 引文。后续成功压缩会生成新 v2 checkpoint。

## 平台自己的运行循环

每批摘要格式或引用校验失败时，会带校验反馈修复一次；第二次失败即停止，不保存新 checkpoint。网络、输出不足和容量错误不作为同预算下的格式修复。每次生成调用仍独立审计，成功写入的摘要调用记录 producedCheckpointId。

    固定快照 → 构建输入 → 计量 / 检查预算 → 保存请求审计 → 调用 Adapter
        ├─ 请求原文 → 校验作用域 → 回取 → 再次构建输入（最多两次）
        ├─ 最终格式错误 → 完整输入修复一次
        ├─ 输出不足 / 网络 / 认证错误 → 暂停
        ├─ 模型上下文超限 → 全阶段压缩并重发一次
        └─ 有效公开回复 → 更新公共记录 → 判断同一候选

格式修复、证据回取和上下文恢复有独立边界，不进行无限重试。原文回取只读取本会话已完成的公共消息，不读取另一成员 memo、内部 trace 或项目文件。

只有所有当前成员接受同一候选作为解决方案且没有不可让步冲突时才生成共识。分歧终局要求相同候选前后两轮均存在同一对成员的双向不可让步立场。更换候选后必须重新交流。

## 操作入口

    /task
    /task goal 讨论平台如何保留用户约束
    /task constraints 不删原文;不把未决分歧写成共识
    /task rebase
    /capacity 1 windowTokens 32768
    /capacity 1 outputReserve 4096
    /capacity 1 extraReserve 2048
    /capacity 1 safetyReserve 512
    /context
    /compact 1
    /recall <公共消息ID>
    /inspect
    /inspect <请求ID>

/task constraints 不带内容可明确清空固定约束。/task rebase 是用户显式改变旧指令边界的操作，模型不能代替用户执行。

网页“共享记录”提供上下文控制台：目标与约束、成员容量、压缩策略、checkpoint 引文及实际请求。模型设置里的“上下文容量”可配置各成员的窗口和预留。窗口来源与计数来源分别显示。

## 评测与当前边界

    npm run eval:context
    npm test
    npm run build

固定场景检查覆盖重复压缩、约束保留、名字冲突、当前轮次压缩、错误引用、公共证据回取、容量、超限恢复和终局判断；完整测试还覆盖 API/A2A、HTTP、持久化、CLI 和凭证。它们验证可复现的运行不变量，不把另一个模型的打分当作证明。

真实模型验证与观察到的失败保护记入 [progress.md](progress.md)。OpenAI/Anthropic 计数协议通过模拟服务验证，没有对应真实 Key 时不宣称真实供应方验证通过。

请求清单包含模型配置与实际平台文本，并不重建原生运行时隐藏的内部提示、工具历史，或保证再次调用得到相同输出。完整请求可能包含用户明确分享的项目文本或成员 memo，保存在本机数据目录，不转发给其他成员。

## 后续完善
